## Tech stack

- **Runtime/framework:** SAP CAP (Cloud Application Programming Model), Node.js, TypeScript (`@cap-js/cds-typescript-plugin`)
- **LLM:** Claude Sonnet via SAP AI Core / Generative AI Hub orchestration API (not a direct Anthropic API key — everything goes through Generative AI Hub)
- **Data:** CDS entities backed by SAP HANA Cloud (free-tier instance); SQLite for local dev
- **Outbound connectivity:** SAP BTP Destination service for *every* external call — S/4HANA (read + write), the AR mailbox (Graph API), and the optional bank statement feed. Never hardcode a URL or credential in application code.
- **Auth:** XSUAA in front of the CAP app
- **Deployment target:** Cloud Foundry, `mta.yaml` / `cf push`
- **UI:** plain HTML/TypeScript SPA (no framework) — deliberately simple, not Fiori Elements, for this PoC

## Architecture: three agents, single responsibility each

Do not blur these boundaries or merge agents' jobs, even when it looks like a shortcut:

1. **Agent 1 — Ingestion** (`srv/agents/ingestion-agent.ts`): polls the AR mailbox (and optionally a bank statement feed) on a schedule, classifies each item as relevant or not, fetches relevant attachments, logs every decision (including what it ignored). Does **not** parse payment fields.
2. **Agent 2 — Extraction** (`srv/agents/extraction-agent.ts`): takes a raw PDF, returns structured payment data (payer, amount, currency, value date, references). Does **not** look at open items or make matching decisions.
3. **Agent 3 — Matching** (`srv/agents/matching-agent.ts`): takes a structured payment + the customer's open items, returns proposed matches with a status (`full` / `probable` / `toBeChecked` / `noMatch`) and a short rationale. Deterministic scoring handles the clear cases; the LLM is only invoked for the ambiguous branch (fuzzy payer-name resolution, free-text remittance memos, explaining the rationale). Does **not** write to S/4 or decide to post.

If a task seems to need a fourth agent or a merge of two of these, stop and raise it rather than deciding unilaterally — the split was a deliberate design choice (see vision doc §1).

## Multi-item posting orchestration

The S/4 `Postings` entity (`zac_posting_moc_o4`) is flat and single-item — one `OpenItemId` per Postings record, no line-items child entity. So when a Payment matches multiple open items, **the CAP layer creates one Postings record per matched open item**, not one multi-line posting. All of a Payment's Postings records are tied together only on our side, via the existing `Payments.matches` composition of `ProposedMatches` (each `ProposedMatches` row carries its own `openItemId`, `companyCode`, and eventually `postingId`/`documentNumber`). S/4 itself has no concept of grouping these — confirmed during Sprint 0 by creating two independent Postings records against two different open items in the same run: distinct `PostingId`s, and nothing in either record's fields (or in `$metadata`) references the other record or a shared batch/payment key. Do not go looking for a batching/multi-item API on the S/4 side — there isn't one; this is a deliberate decision, not a gap to fill later.

## Non-negotiable rules

- **No autonomous posting.** The CAP service only calls the S/4 clearing/posting API after a human has approved a specific proposed match via the UI. Never wire an agent's output directly to the posting endpoint.
- **All outbound calls go through the Destination service.** No hardcoded hostnames, API keys, or OAuth secrets in code — not even "temporarily for testing."
- **Never commit secrets.** `.env`, service keys, and any downloaded credentials are in `.gitignore` and `.claudeignore`. If you need a secret to test something, ask rather than inventing a placeholder that looks real.
- **The S/4 write (clearing) API is unvalidated — treat it as a spike, not a dependency.** Community reports conflict on whether it reliably supports AR/customer open items on Public Cloud. `srv/s4/clearing-client.ts` must have a working fallback path (stage the approved match for manual completion in the standard S/4 "Clear Customer Open Items" Fiori app) if the direct API call isn't reliable on this tenant.
- **`simulatePosting` is not a pre-approval dry run — it requires an already-created `Postings` record.** It's bound to a single, existing `PostingsType` instance (confirmed via a clean `500` when called with no key — see Sprint 0 checklist), so there is no way to preview a posting before it exists. Treat "create a `Postings` record" as the actual posting action itself; `postClearing` (`srv/s4/clearing-client.ts`) calls `simulatePosting` automatically right after create, in the same flow, to get final `status`/`documentNumber`/`SAP__Messages` — not as two separate user-facing steps, and not as a way to avoid creating a real record.
- **Low-confidence output routes to `toBeChecked`, never to a guessed `full`/`probable`.** This applies to both Agent 1 (uncertain classification) and Agent 3 (uncertain match) — silently guessing on a financial matching decision is worse than asking a human.

## Conventions

- TypeScript everywhere in `srv/`; no `any` unless genuinely unavoidable — the whole point of typed CDS entities is that agent tool schemas and CAP function signatures share one source of truth.
- Each agent module exports a plain async function with a typed input/output — no hidden shared state between agents.
- Every agent gets a handful of fixture-based tests (fixed input → expected output) alongside it, especially Agent 2 and Agent 3, since these depend on LLM output and need a regression net when prompts change.
- Keep prompts for each agent in the same file as the agent logic (not a separate prompts directory) — they're small enough, and colocated is easier to keep in sync with the tool schema.
- Log tool-call/result pairs for every agent invocation (this is the "transparency panel" data referenced in the vision doc) — don't skip this for speed.
